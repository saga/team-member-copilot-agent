我实际检查了当前 `main` 的实现后，结论比较明确：

**现在这套代码已经把“Team Chat 的可靠运行时”做得比较完整，但还没有把“任务”作为一等对象。**

当前链路本质上是：

```text
用户消息
  ↓
ConversationMessage
  ↓
GroupDispatcher
  ↓
谁被唤醒
  ↓
MemberTurnScheduler
  ↓
Execution
  ↓
MemberRuntime / Copilot Session
  ↓
回复或 <NO_REPLY>
```

而你真正需要的是：

```text
用户进入 Team Conversation
  ↓
识别“这是要做什么”
  ↓
自动收集已有 context
  ↓
只问真正缺失、会阻塞执行的问题
  ↓
形成 Task Brief
  ↓
用户确认
  ↓
生成可执行 Plan
  ↓
Lead Member + Specialist Members 分工
  ↓
执行 / 验证 / 修正
  ↓
达到 Definition of Done
  ↓
完成
```

所以**不要继续往现在的 `group-dispatcher + prompt` 上堆规则**。核心改造是：

> **Conversation 是交互容器，Task/Work Session 才是“做事”的状态机。**

微软 Copilot Studio 当前的 generative orchestration 也是把用户输入转成结构化计划、自动补齐缺失输入、再串联 tools/topics/agents，而不是把所有能力都当成普通聊天。([Microsoft Learn][1])
最近的多 Agent 澄清研究也显示，集中管理 clarification、提前收集必要信息，可以减少重复对话并提高任务完成率；MAC 在 MultiWOZ 2.4 上报告了更高的 task success 和更少的平均对话轮数。([ACL Anthology][2])

# 1. 先解决最大的架构问题：Conversation ≠ Task

当前：

```text
Conversation
 ├── messages
 ├── members
 ├── executions
 └── externalWorkRef
```

建议改成：

```text
Conversation
 ├── messages                 // 人与 Agent 的对话
 ├── members
 ├── executions              // runtime 执行记录
 └── activeWorkSessionId
          │
          ▼
     WorkSession
     ├── objective
     ├── requirements
     ├── assumptions
     ├── acceptanceCriteria
     ├── leadMember
     ├── status
     └── tasks[]
            │
            ├── Task A
            │    ├── assignee
            │    ├── dependencies
            │    ├── acceptance
            │    └── executions[]
            │
            ├── Task B
            └── Task C
```

最重要的是：

```text
Conversation = “我们说了什么”
WorkSession = “我们现在到底要完成什么”
Task        = “为了完成它需要做哪些事情”
Execution   = “某个 Agent 实际跑了一次”
```

当前 `Execution` 已经很好地表达了最后一层，但**不能拿 Execution 当 Task**。

---

# 2. 不要重新定义现在的 `Conversation.kind`

现在已经有：

```ts
type ConversationKind = 'direct' | 'group' | 'work';
```

不要把 `work` 扩展成“多人团队任务”。

增加一个正交概念：

```ts
export type ConversationMode =
  | 'discussion'
  | 'task';
```

于是：

```text
kind                  mode
----------------------------------
direct                task
group                 discussion
group                 task
work                  task
```

实际最重要的是：

```text
group + task
```

也就是：

> 多个 Agent 在一个共享对话里，为一个明确目标协作。

这样现有的 `group = discussion` 逻辑可以保留，不会把老功能全部推翻。

---

# 3. 我建议 Team Conversation 默认进入 Task Mode

现在用户创建 group 后，实际语义是：

> “大家来聊一聊。”

所以 `GroupDispatcher` 才会做：

```text
user message
    ↓
Everyone
    ↓
所有 Member 自己决定是否 <NO_REPLY>
```

这个模型天然容易变成：

```text
User
  ↓
Alice
  ↓
Bob
  ↓
Charlie
  ↓
Alice
  ↓
Bob
```

最后没有任何事情真正结束。

### 新设计

Team conversation 默认：

```text
Task Mode
```

只有显式选择：

```text
Discussion
```

才进入现在的自由讨论模式。

UI：

```text
Conversation

[ Task ] [ Discussion ]
```

或者更简单：

```text
New Team Conversation
    ○ Work on a task     ← default
    ○ Open discussion
```

这样从产品层面就已经把“闲聊”和“干活”分开了。

# 4. WorkSession 是整个设计的核心

增加：

```ts
export type WorkSessionStatus =
  | 'intake'
  | 'clarifying'
  | 'ready'
  | 'planning'
  | 'executing'
  | 'waiting_user'
  | 'blocked'
  | 'verifying'
  | 'completed'
```

```ts
export interface WorkSession {

  assumptions: TaskAssumption[];

  missingRequirements: MissingRequirement[];

  acceptanceCriteria: AcceptanceCriterion[];
```

# 5. Requirements 不要做成一个自由文本

这是整个“快速澄清”的关键。

不要：

```text
Context:
xxxxx
```

而要有结构化需求状态。

例如：

```ts
interface TaskRequirements {
  goal: Fact<string>;
  scope: Fact<string> | null;
  stakeholders: Fact<string[]> | null;

  constraints: Fact<string[]>;

  deadline: Fact<string> | null;

  deliverable: Fact<string> | null;

  successCriteria: Fact<string[]>;

  relevantContext: Fact<string[]>;

  nonGoals: Fact<string[]>;

  priority: Fact<string> | null;
}
```

每个 Fact 都带来源：

```ts
interface Fact<T> {
  value: T;

  source:
    | 'user'
    | 'conversation'
    | 'jira'
    | 'knowledge'
    | 'memory'
    | 'agent_inference';

  confidence: number;

  confirmedByUser: boolean;

  updatedAt: string;
}
```

这点非常重要。

例如：

```text
目标
来源：用户
确认：是
```

和：

```text
目标
来源：Agent inference
确认：否
```

完全不是一回事。

# 6. Agent 不应该一进入对话就开始“回答”

这里是当前最应该改的地方。

现在 `ContextAssembler` 对 direct turn 会生成：

```text
Current message:
...

Answer the message directly and concisely.
```

而 group 则是：

```text
You are one participant among several...
```

这两个 prompt 都是在指导：

> “怎么回话。”

而不是：

> “怎么把事情完成。”

应增加一个新的 `turnMode`：

```ts
type TaskTurnMode =
  | 'intake'
  | 'clarification'
  | 'planning'
  | 'execution'
  | 'verification'
  | 'final';
```

于是第一轮不是：

```text
Answer the user.
```

而是：

```text
You are the lead member for this work session.

Your first responsibility is to determine what the user wants the team to accomplish.

Do not start execution until the task is sufficiently specified.

First:
1. extract the objective;
2. identify information already available from the conversation, Jira, knowledge and team context;
3. identify only the missing information that blocks planning or execution;
4. ask the smallest useful set of clarification questions.

Do not ask the user for information that can be obtained from available systems.
Do not ask broad "tell me more" questions.
Prefer concrete questions with sensible defaults.
```

# 7. Agent Team 不能让所有 Member 一起负责澄清

这是第二个非常关键的设计。

必须有：

```text
Lead Member
```

只有 Lead Member 负责和用户澄清需求。

而不是：

```text
User
 ↓
Alice asks question
 ↓
Bob asks another question
 ↓
Charlie asks another question
```

这会非常糟糕。

正确模型：

```text
                 ┌───────────────┐
                 │ WorkSession   │
                 └───────┬───────┘
                         │
                    Lead Member
                         │
                  user clarification
                         │
               ┌─────────┴─────────┐
               │                   │
          Specialist A         Specialist B
```

专家可以参与分析，但**不要直接轮流向用户提问**。

如果专家发现缺信息：

```text
Expert
  ↓
clarification request
  ↓
Lead Member
  ↓
User
```

这也是目前多 Agent clarification 研究特别关注的地方：不仅要决定“问什么”，还要决定“谁来问”。([ACL Anthology][2])

# 8. 如何做到“尽快澄清”

不是让 Agent 问一大堆问题。

我建议固定成这套策略。

## 第一原则：先自己找

优先级：

```text
用户已经说过
    ↓
当前 Conversation
    ↓
Jira / External Work
    ↓
Team Knowledge
    ↓
Member Memory
    ↓
Agent inference
    ↓
User clarification
```

例如用户说：

> 帮我处理 ABC-123 登录超时问题。

不要问：

> ABC-123 是什么？

因为系统已经可以通过 Jira provider 获取。

也不要问：

> 这个问题的背景是什么？

因为 Jira description/comment 可以获取。

最终可能只剩：

```text
我已经读取 ABC-123 的现有信息。

执行前还需要确认两个会影响方案的问题：

1. 需要修复哪个环境？
   [测试] [生产] [两个都要]

2. 什么算完成？
   [错误率恢复正常]
   [用户投诉消失]
   [你有其它标准]
```

这就是你真正需要的“快速澄清”。

Microsoft Copilot Studio 的 generative orchestration 也采用类似思路：根据 action/topic/agent 的输入参数识别缺失信息，再自动补问，而不是每轮从头收集。([Microsoft Learn][1])

# 9. 澄清问题必须有“阻塞等级”

不要把所有缺失字段都当成必须问。

增加：

```ts
interface MissingRequirement {
  field: string;

  reason: string;

  blocking: boolean;

  question: string;

  suggestedAnswers?: string[];

  source?: string;
}
```

例如：

```text
goal              present
scope             present
environment       missing / blocking
deadline          missing / non-blocking
stakeholders      missing / non-blocking
output_format     missing / non-blocking
```

那么：

```text
hardMissing != 0
```

才停止执行。

否则：

```text
softMissing != 0
```

可以直接采用默认值：

```text
我暂按周五完成，并以最终报告作为交付物。
```

让用户纠正即可。

---

# 10. 每轮最多问 2～3 个问题

不要：

```text
1. 背景是什么？
2. 目标是什么？
3. 用户是谁？
4. 环境是什么？
5. deadline？
6. 成功标准？
7. 风险？
8. 输出格式？
```

这会让用户感觉自己在填写需求文档。

建议：

```text
每次 1～3 个问题
```

并且优先问：

> 会阻塞下一步执行、而且只有用户能回答的问题。

例如：

```text
我已经把 Jira、Team Knowledge 和现有讨论中的信息合并了。

现在只有两个问题会阻塞执行：

1. 目标环境？
2. 成功标准？

其它细节我会按团队默认规则处理。
```

研究中的 MAC 也采用“主动获取必要信息、减少重复澄清”的方向，并报告了减少平均对话轮数的结果。([ACL Anthology][2])

---

# 11. 不要问开放式问题，尽量提供默认值

不要：

> 请进一步描述您的需求。

改成：

> 你希望我们最终交付什么？

然后：

```text
[修复方案]
[代码修改]
[分析报告]
[上线]
[以上全部]
```

用户也可以自由输入。

所以 UI 可以支持：

```text
Clarification Card

环境
○ Development
○ Test
○ Production
○ All

成功标准
○ Tests pass
○ Error rate < 1%
○ User confirmed
○ 自定义
```

这比单纯聊天快很多。

# 12. 第一轮之后要产生 Task Brief

当需求足够完整时，不要立刻执行。

先产生一个结构化 Brief：

```text
┌─────────────────────────────────────┐
│ Task Ready                           │
├─────────────────────────────────────┤
│ Goal                                 │
│ 解决 ABC-123 登录超时问题            │
│                                     │

│                                     │

│ 修复代码 + 测试 + 发布               │
│                                     │
│ Success criteria                    │
│ 登录成功率 > 99%                    │
│                                     │

│ 使用现有认证架构                     │
│                                     │

│ Alice Lead                          │
│ Bob Backend                         │
│ Carol QA                            │
│                                     │

└─────────────────────────────────────┘
```

用户确认：

```text
开始执行
```

才进入：

```text
planning
```

# 13. Plan 也必须成为数据库对象

不要把 Plan 只存在 LLM context 里。

```ts
interface WorkTask {
  id: string;
  workSessionId: string;

  parentTaskId: string | null;

  title: string;
  objective: string;

  assigneeMemberId: string | null;

  status:
    | 'pending'
    | 'ready'
    | 'running'
    | 'waiting_user'
    | 'blocked'
    | 'verifying'
    | 'completed'
    | 'failed';

  dependencies: string[];

  acceptanceCriteria: AcceptanceCriterion[];

  result: unknown | null;

  sortOrder: number;

  version: number;
}
```

这样一个任务可以变成：

```text
Task
 ├── 1. Investigate
 ├── 2. Implement
 ├── 3. Test
 ├── 4. Review
 └── 5. Deploy
```

其中：

```text
1 → 2 → 3 → 4 → 5
```

也可以：

```text
        ┌→ 2 Backend ─┐
1 Analyze              ├→ 4 Review → 5 Deploy
        └→ 3 QA ──────┘
```

这才是真正的 Team Agent。

# 14. `Execution` 不要删除，反而要更明确

你现在已经有：

```text
Execution
parentExecutionId
delegationPath
runtimeId
status
retry
```

这些都很好。

增加：

```ts
taskId: string | null;
taskStepId: string | null;
```

然后语义变成：

```text
WorkSession
   ↓
Task
   ↓
TaskStep
   ↓
Execution
   ↓
MemberRuntime
   ↓
Copilot Session
```

这是整个系统最干净的层次。

# 15. 不要把 `Execution.completed` 当成“任务完成”

这是必须严格分开的。

当前：

```text
Execution completed
```

只表示：

> Agent 这一轮运行结束。

不代表：

> 用户要求的事情已经完成。

必须增加：

```text
Task verification
```

例如：

```ts
interface TaskVerification {
  taskId: string;

  criteria: Array<{
    id: string;
    description: string;
    status: 'passed' | 'failed' | 'unknown';
    evidence: string[];
  }>;

  verifiedBy: string;

  verifiedAt: string;
}
```

最后：

```text
Execution completed
        ↓
Task result produced
        ↓
Verification
        ↓
Acceptance criteria all passed
        ↓
Task completed
```

没有这层，Agent 很容易出现：

> “我已经完成了。”

但是其实只写了代码，没测试；或者查到了信息，但没有解决问题。

# 16. `TaskDecision` 不要污染现在的 `ExecutionDecision`

当前：

```ts
type ExecutionDecision = 'reply' | 'skip';
```

这个很好，继续保留。

新增：

```ts
type TaskDecision =
  | 'clarify'
  | 'update_requirements'
  | 'propose_plan'
  | 'start_task'
  | 'delegate'
  | 'continue'
  | 'wait_user'
  | 'verify'
  | 'complete'
  | 'blocked';
```

所以：

```text
TaskDecision
    ↓
决定“接下来业务上要做什么”

ExecutionDecision
    ↓
决定“这一轮 Agent 要不要说话”
```

不要混在一起。

# 17. Team 的真正执行架构应该变成这样

```text
                         Conversation
                              │
                              ▼
                     WorkSessionCoordinator
                              │
             ┌────────────────┼────────────────┐
             │                │                │
          Intake          Planner          Verifier
             │                │                │
             ▼                ▼                ▲
       Lead Member       Task DAG           evidence
             │                │
             └───────┬────────┘
                     │
              ready TaskStep
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Member A   Member B   Member C
          │          │          │
          ▼          ▼          ▼
      Execution   Execution   Execution
          │          │          │
          └──────────┼──────────┘
                     ▼
                 Task result
                     │
                     ▼
                  Verify
                     │
             ┌───────┴────────┐
             │                │
           passed           failed
             │                │
             ▼                ▼
         next step         repair task
```

这里真正控制流程的是：

```text
WorkSessionCoordinator
```

不是 LLM。

LLM 负责：

```text
理解
推理
生成计划候选
解释
提问
选择专业 Member
```

而系统负责：

```text
状态
权限
任务阶段
依赖
调度
完成条件
恢复
审计
```

这和 OpenAI Agents SDK 当前把 agents、handoffs、guardrails、structured outputs 作为运行时原语的方向是一致的，但你这里仍然应该把业务 Task 状态放在自己的 control plane，而不是只交给 agent session。([OpenAI GitHub Pages][3])

# 18. 最重要的修改：GroupDispatcher 必须改变

当前 `server/group-dispatcher.ts`：

```text
group
 + user message
 + no mention
       ↓
Everyone
```

这正是“无目的闲聊”的主要来源之一。

改成：

```ts
if (conversation.mode === 'task' && activeWorkSession) {
  return {
    wakes: [
      {
        memberId: activeWorkSession.leadMemberId,
        reason: 'task_lead',
        triggerSequence: message.messageSequence,
      }
    ]
  };
}
```

只有：

```text
explicit @Bob
```

或者：

```text
TaskCoordinator schedules Bob's task step
```

才唤醒 Bob。

于是：

```text
用户说一句话
```

不会再：

```text
Alice
Bob
Carol
David
```

全部醒来。

# 19. `@member` 在 Task Mode 也应该重新定义

当前：

```text
@Bob
```

= “Bob 你来回答”。

Task Mode 更合理：

```text
@Bob
```

= “把这件事交给 Bob / 咨询 Bob”。

由 Lead Member / Coordinator 转成：

```text
TaskStep
assignee = Bob
```

而不是立即把 Bob 拉进聊天。

这样：

```text
@QA
帮我检查一下这个方案
```

变成：

```text
Create TaskStep
  title: Review proposed solution
  assignee: QA
  parentTask: currentTask
  acceptance:
    - identify defects
    - provide test coverage gaps
```

# 20. 多件事如何处理

这是你特别提到的“一件事或者多件事”。

比如用户：

> 帮我分析这个问题，再写一个修复方案，同时整理一份给管理层的报告。

不要继续当成一条 chat。

应该抽取：

```text
WorkSession
  Goal: 解决并汇报这个问题

  Tasks:
    A 分析问题
    B 制定修复方案
    C 管理层报告
```

依赖：

```text
A
├──> B
└──> C
```

因为 B/C 都依赖 A。

再例如：

> 同时帮我检查 A、B、C 三个服务。

可以：

```text
           Analyze
         /    |    \
        A     B     C
         \    |    /
           Summary
```

这样真正实现多 Agent 并行。

# 21. “一个 Conversation 多任务”也不要混成一个任务

我建议：

```text
Conversation
  ├── WorkSession #1  登录问题
  ├── WorkSession #2  性能优化
  └── WorkSession #3  发布准备
```

但：

```text
只允许一个 active WorkSession
```

默认。

如果用户突然：

> 顺便帮我看看另外一个 API。

Agent 应该说：

> 这是一个独立目标，我建议创建一个新的任务，当前任务先保持不变。

UI：

```text
Current Work
────────────────
登录问题      ● Executing

Other Tasks
────────────────
性能优化      ✓ Completed
API 检查      Draft
```

这样一个长时间 Team Conversation 也不会失控。

# 22. 首次进入 Conversation 的完整流程

建议最终做到：

```text
用户：
帮我把登录问题解决掉
```

系统：

```text
① Intake

已识别：
- Jira: ABC-123
- 目标：解决登录失败
- 当前状态：Open
- 环境：Production（来自 Jira）
```

```text
Capabilities
```
```text
Knowledge
Memory
```


真正缺的是中间这一层：

```text
             ★ WorkSession / Task Control Plane ★
```

一旦补上这一层，前面你一直在讨论的很多问题都会自然统一：

```text
“Agent 为什么被唤醒？”
        → TaskStep / Lead

“为什么这个 Member 要问用户？”
        → Clarification owner

“什么时候该停止聊天？”
        → Task state

“什么时候算完成？”
        → Acceptance criteria + Verification

“多个 Member 怎么协作？”
        → Task DAG

“为什么一直闲聊？”
        → 没有 active task / 没有 task state

“为什么 Agent 总问重复问题？”
        → structured requirements + provenance

“Jira / Knowledge 怎么进入业务 context？”
        → Intake / Context resolver

“Execution completed 为什么事情没完成？”
        → Execution 和 Task 分层
```

外部成熟实现也是这个方向：Microsoft 把生成式编排建立在“意图 → 缺失输入 → 计划 → 多能力执行”之上；OpenAI Agents SDK 把 session、handoff、structured output、guardrail 分开；任务型对话研究则长期围绕 intent、slot、dialogue state 与 clarification 展开。([Microsoft Learn][1])

代码上最值得先读和改的几个位置是 `server/group-dispatcher.ts`、`server/team-service.ts`、`server/context-assembler.ts`、`server/domain.ts`、`src/components/team/MessageComposer.tsx`；当前实现可以直接在这些基础上演进，不需要推翻现有 Execution / Runtime / SSE 架构。
