结合你现在这个 `team-member-copilot-agent`，我建议不要把“自我进化”理解成“Member Agent 自己修改模型参数”。截至 2026 年，比较成熟的方向其实是：

> **让 Agent 从实际工作中积累 Experience，经过反馈和评估，把 Experience 沉淀成 Memory / Skill / Retrieval Strategy；只有更高阶段才进入离线 RL / fine-tuning。**

这和你现在的架构非常契合。近期综述也把现代 self-improvement agent 基本看成“foundation model + prompt + memory + tools + control logic”的持续更新系统，而不只是模型权重变化。([arXiv][1])

## 1. 最值得你实现的是这条闭环

你现在用户可以在 Chat 里说：

> “这个 Member 总是把 Jira Story 和 Subtask 混在一起。”
> “以后遇到这种需求，先检查 acceptance criteria。”
> “刚才的分析漏掉了合规限制。”

不要直接把这句话 append 到 `MEMORY.md`。

应该变成：

```text
用户反馈
   ↓
Feedback Event
   ↓
归因 / 分类
   ├─ 临时上下文问题
   ├─ 用户偏好
   ├─ 事实/知识
   ├─ 工作方法错误
   ├─ Skill 缺陷
   └─ Tool / 系统问题
   ↓
Experience
   ↓
Reflection / Consolidation
   ↓
Candidate Memory / Candidate Skill / Retrieval Rule
   ↓
Evaluation
   ↓
Approve / Reject
   ↓
正式生效
```

这比“聊天中反馈一句 → 修改人格 Prompt”可靠得多。

# 2. 目前最值得借鉴的几条研究路线

### Reflexion：最早的“语言强化学习”

Reflexion 不更新模型权重，而是把任务反馈转化成 verbal reflection，然后放进 episodic memory，下一轮利用。这个思路和你说的“有点像强化学习”最接近。([arXiv][2])

对你的系统可以直接对应：

```text
Task failed
↓
Member 反思
↓
Experience:
“处理 Jira Story 时先读取现有 Subtask，避免重复规划”
↓
下次执行检索 Experience
```

它的价值在于：**无需训练模型即可产生跨任务改进。**

---

### ReasoningBank：不要只存“记忆”，要存“可复用策略”

ReasoningBank 进一步强调，把成功和失败轨迹抽象成可泛化的 reasoning strategy，再在后续任务里检索。论文报告它在 web browsing 和 software engineering 上优于只保存原始 trajectory 或只保存成功流程的 memory 方法。([arXiv][3])

这特别适合你的 Member。

不要保存：

```text
“2026-09-27 ABC-123 出现了问题……”
```

而应该逐渐形成：

```text
Strategy:
当处理已有 Jira Story 时：
1. 先读取 Story
2. 再读取已有 Subtask
3. 对比当前 Task plan
4. 只补充缺失工作
5. 不复制已有工作
```

这是 **Experience → Skill**。

---

### SkillWeaver / SAGE：真正把经验变成 Skill

SkillWeaver 的路线非常接近你现有系统：Agent 从执行过程中发现、练习、抽象出可复用 Skill，并持续扩充 Skill library。研究中 Skill 可以跨 Agent 复用。([arXiv][4])

你现在已经有：

```text
global skill
team skill
member skill
```

所以其实已经有了一个很好的“自我进化载体”。

未来可以出现：

```text
global/
team/
member/
generated/
```

例如：

```text
member/<member-id>/skills/
    jira-story-analysis/
    financial-review/
    ...

generated/
    jira-story-reconciliation/
```

但 **generated skill 绝不能直接生产生效**。

应该：

```text
generated candidate
        ↓
evaluation
        ↓
human approval / trusted auto-approval
        ↓
published skill version
```

Anthropic 2025 年介绍 Agent Skills 时，也明确把 Skill 定义为“可组合的 instructions + scripts + resources”，并建议通过实际工作过程逐步捕获成功方法和常见错误。([Anthropic][5])

Anthropic 2026 年介绍 Warp 的实践也非常接近这一模式：捕获 human feedback → 转成 skill update → 用在后续任务中。([Anthropic][6])

# 3. 2026 年一个很重要的变化：不要只让 Memory 增长

EvolveMem 很值得你关注。

它指出传统 memory 系统一个明显问题：

```text
memory 在变化
但是
retrieval 方法永远不变
```

他们让系统根据失败日志自动分析 retrieval 的问题，再调整：

```text
ranking
fusion
retrieval strategy
answer generation policy
```

而且有 **自动回滚和防止 regression**。([arXiv][7])

这对你的平台意味着：

不要只做：

```text
Member Memory
```

还应该逐渐有：

```text
Experience Memory
+
Retrieval Policy
```

比如 Member 总是找不到：

```text
financial-core
```

里的相关资料。

系统可以发现：

```text
最近 30 次任务：
knowledge search hit rate 很低
```

然后自动实验：

```text
query rewrite
topK
reranking
source preference
```

而不是让 Agent 永远继续犯同样的检索错误。

# 4. MemRL 更接近你说的“强化学习”

2026 年的 MemRL 提出了一个很直接的方向：

> 不修改模型参数，而是在 episodic memory 上做 runtime reinforcement learning。

其核心是让 Agent 根据环境反馈学习哪些历史经验值得再次使用，从而避免简单 semantic retrieval 把噪声也捞回来。([arXiv][8])

这和你的系统尤其匹配，因为：

```text
LLM
↓
Experience Memory
↓
retrieval
↓
执行
↓
task outcome
↓
reward
↓
更新 experience utility
```

你甚至不需要真正做 RL algorithm。

第一版可以非常简单：

```text
experience.utility
experience.successCount
experience.failureCount
experience.lastUsedAt
experience.qualityScore
```

然后：

```text
成功使用 → +1
失败使用 → -1
人工明确认可 → +3
人工指出错误 → -3
长期未使用 → decay
```

已经是一个非常实用的“轻量 RL”。

# 6. 我最建议你给 Member 加的不是“Self Learning”，而是 5 种学习对象

这是你这个平台最适合的划分。

### A. Preference

```text

```

特点：

```text

直接影响回答风格
```

### B. Fact

例如：

保存：

```text

```

但它应该有：

```text
source
confidence
createdAt
expiresAt
```

不能无限相信。

---

### C. Experience

例如：

> “上次处理这种 Jira Story 时，直接创建任务导致重复；应该先读取 Subtask。”

这是最重要的。

```text

trigger = jira_story_with_existing_subtasks
```

### D. Skill Candidate

```text

```

然后生成：

```text

```

但先进入：

```text

```

而不是直接覆盖 Member。

---

### E. Retrieval / Routing Learning

例如：

```text

→ financial-core
→ compliance KB
→ architecture KB
```

Agent 多次发现：

```text
compliance KB 的命中率明显更高
```

可以学习：

```text
query → preferred source
```

这比不断修改 Prompt 更有效。

# 10. 还可以做“反向学习”：成功也要学习

不能只有错误反馈。

例如：

```text
Task completed
Acceptance criteria = 100%
User = 👍
```

系统自动抽取：

```text
Strategy:
对于类似任务，先读取 X，再调用 Y，最后用 Z 验证。
```

这样 Experience Library 不只是：

```text
avoid mistakes
```

而是：

```text
what works
+
what fails
```

这与 ReasoningBank / FLEX 的方向一致。FLEX 强调把成功和失败持续抽象成可继承的 experience library，而且可以跨 Agent 继承。([arXiv][10])

# 11. “自我进化”最好分三级，而不是一次做到 RL

### Level 1：Experience Memory

你现在就可以做。

```text
用户反馈
→ Experience
→ Retrieval
```

不修改 Skill。

这是第一阶段。

---

### Level 2：Skill Evolution

积累足够 Experience 后：

```text
Experience
→ Skill Candidate
→ Eval
→ versioned Skill
```

这时 Member 真正开始“变得更会做某类工作”。

这是我最推荐你的目标。

---

### Level 3：Model / RL Evolution

最后才是：

```text
trajectory dataset
→ reward
→ GRPO / RL
→ fine-tune model
```

这是平台级离线过程，不应该在生产 Member 对话里直接发生。

Agent0 这类研究已经在探索自动构造 curriculum + executor 的持续 RL 演化，但它更属于模型训练研究基础设施，不适合直接嵌进你现在的生产 Team runtime。([arXiv][11])

# 13. 最重要的一条：一定要有 Eval Gate

这是整个“自我进化”最容易做错的地方。

不能：

```text
用户说一句
   ↓
Agent 修改 Skill
   ↓
以后所有任务直接用
```

否则很快会：

```text
错误反馈
→ 错误记忆
→ 错误 Skill
→ 更多错误
→ 自我强化
```

Anthropic 最新的 Agent eval 实践明确强调，持续评估是防止“修一个问题又引入另一个问题”的关键，而且 evaluation 的价值会随 Agent 生命周期累积。([Anthropic][12])

你应该做：

```text
Candidate improvement
       ↓
回放历史相关 Task
       ↓
baseline vs candidate
       ↓
success rate
cost
latency
tool errors
user correction rate
       ↓
publish / reject / rollback
```

EvolveMem 本身就采用了类似的“诊断 → 调整 → 回归检测 → 回滚/继续探索”的闭环。([arXiv][7])
