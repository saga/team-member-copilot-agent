## 先说结论

你的架构里应该明确采用：

> **Goal 可修改，但修改必须产生新的 Goal Revision；旧 Goal 永远不改。Goal Revision 是 Task 和 Execution 的业务输入版本。**

而且我建议不是做一个很重的 workflow/versioning 系统，只增加一个很轻的：

```text
Conversation
    ↓
Goal v1
    ├── Task A(v1)
    ├── Task B(v1)
    └── Execution(v1)

用户修改 Goal
    ↓
Goal v2
    ├── 旧 v1 Task 停止继续推进
    ├── 新 Task(v2)
    └── 新 Execution(v2)
```

这是目前这个 Team Agent 最值得补的一块。

直接写入：

而且明确限制：

```ts
if (this.list(input.conversationId).length > 0) {
  throw badRequest('这个工作区已经存在任务，不能重新创建任务计划');

```

也就是说：

> **当前 Goal 本质上是“初始计划时写一次的字段”。**

后面虽然 `requestClarification()` 可以修改 `requirements_json`，但它不会形成 Goal 历史版本；`conversation.objective` 也没有正常的更新 API。

另外当前 Conversations API 只有：

```text

```

没有：

```text
PATCH /conversations/:id/goal
GET   /conversations/:id/goal/history
```

所以现在会出现一个比较实际的问题：

```text
用户最开始：
“分析 A 产品风险”
```

# 2. 其它 Agent / Team Framework 是怎么做的

这里有一个很重要的共性：

**成熟 Agent Framework 通常有“持久化 State / Checkpoint / Session”，但不会替你的业务系统定义一个“Goal Revision”领域对象。**

也就是说：

> Framework 负责“状态可以变化、可以恢复、可以回放”；
> **业务系统负责“Goal 到底是什么、什么时候变了、哪个 Task 属于哪个 Goal”。**

## LangGraph

LangGraph 的核心是 checkpoint。

每个 super-step 都可以保存 graph state，并支持 human-in-the-loop、fault tolerance、time travel；还可以从历史 checkpoint fork 出新的状态。也就是说，**状态变化天然是有历史边界的**。([GitHub][1])

但它不会替你的业务定义：

```text
Goal v1
Goal v2
Goal v3
```

这仍然需要应用自己放进 state / database。

所以对你的架构，LangGraph 给出的启发是：

> **不要修改历史 execution 的输入状态。新的 Goal 应该成为新的状态边界。**

---

## Microsoft Agent Framework

Microsoft Agent Framework 的 Workflow State 可以被多个 executor 共享和修改；workflow 本身和 workflow state 是分开的，而且构建完成后的 workflow 不应该在运行过程中直接修改。它也支持 checkpoint + HITL request/resume。([Microsoft Learn][2])

这个设计非常接近你现在的想法：

```text
Workflow definition
        ≠
Workflow runtime state
```

类比到你的系统：

```text
Member / Skill / Capability
        ≠
Conversation Goal / Task State
```

所以 Goal 修改应该是：

```text
修改 runtime/business state
```

而不是：

```text
修改 Agent definition
```

---

## AutoGen

AutoGen 的 Team 可以 `save_state()` / `load_state()`，Human-in-the-loop 也可以：

```text
Team run
    ↓
暂停
    ↓
保存 state
    ↓
用户反馈
    ↓
恢复 Team
```

官方 Team state 还有自己的 state schema/version 字段。([Microsoft][3])

但这里的 `version` 是 **state schema/version**，不是：

```text
Business Goal version
```

所以你不能简单地认为“用了 AutoGen state version 就等于 Goal version”。

---

## Google ADK

ADK 很强调 Event + State。

状态变化通过：

```text
Event
  +
state_delta
```

进入 Session history，并由 SessionService 持久化；官方还特别强调不要直接偷偷修改持久化 Session 的 state，否则会绕过 event tracking、audit 和 persistence。([GitHub][4])

这对你的架构启发很大：

> **Goal 修改应该是一个正式的 domain mutation，而不是 Lead 在 prompt 里临时“认为现在 Goal 变了”。**

---

## CrewAI

CrewAI 更偏 Task-centric：

```text
Task
  description
  expected_output
  agent
  context
```

任务定义本身就是主要的业务执行单元。([GitHub][5])

这类框架很适合：

```text
Goal
 ↓
Task list
 ↓
Crew execution
```

但对于你这种：

```text
长生命周期 Conversation
+ 多 Member
+ 并发 Task
+ Human 后续修改需求
+ 审计
+ 外部系统副作用
```

不能只依靠 Task description 来代表 Goal。

---

## OpenAI Agents SDK

OpenAI Agents SDK 当前把：

```text
Agent
Runner
Session
RunState
HITL interruption
```

分开管理；Session 负责持久上下文，RunState 可以保存和恢复运行状态。([OpenAI][6])

同样，它提供的是 runtime/session primitive，并不是金融业务意义上的：

```text
Goal Revision
```

# 3. 所以你的 Goal 应该是什么

建议明确划分：

```text
Goal
 ├── objective
 ├── requirements
 │    ├── facts
 │    ├── assumptions
 │    ├── constraints
 │    └── successCriteria
 └── revision
```

现在你的：

```ts
objective
requirements
```

其实已经天然组成一个 Goal。

所以不要只给：

```text
objective version
```

而是：

> **Objective + Requirements 一起版本化。**

否则会出现：

```text
Goal v2 objective
+
Goal v1 successCriteria
```

这种非常危险的半更新状态。

# 4. 我建议的数据结构

## Conversation 增加

```ts
export interface Conversation {
  ...
  objective: string;
  requirements: TaskRequirements;

  /** 当前生效的 Goal revision */
  goalRevision: number;

  ...
}
```

数据库：

```sql
ALTER TABLE conversation
ADD COLUMN goal_revision INTEGER NOT NULL DEFAULT 1;
```

---

## 新增 `conversation_goal_revision`

不要做完整 event sourcing，只增加一张历史表。

```sql
CREATE TABLE conversation_goal_revision (
  id TEXT PRIMARY KEY,
  conversation_id TEXT NOT NULL,

  revision INTEGER NOT NULL,

  objective TEXT NOT NULL,
  requirements_json TEXT NOT NULL,

  changed_by_type TEXT NOT NULL
    CHECK (changed_by_type IN ('user', 'member', 'system')),

  changed_by_id TEXT NOT NULL,

  reason TEXT NOT NULL DEFAULT '',

  change_kind TEXT NOT NULL
    CHECK (
      change_kind IN (
        'initial',
        'clarification',
        'scope_change',
        'success_criteria_change',
        'correction'
      )
    ),

  created_at TEXT NOT NULL,

  UNIQUE (conversation_id, revision),

  FOREIGN KEY (conversation_id)
    REFERENCES conversation(id)
    ON DELETE CASCADE
);
```

注意：

**旧 Revision 永不 UPDATE。**

只：

```text
INSERT v1
INSERT v2
INSERT v3
...
```

# 7. Goal 修改后，旧 Task 不能继续无条件执行

这是整个设计里最关键的一条。

不能做成：

```text
Goal v1
Task A/B/C 正在执行

用户改 Goal → v2

Task A/B/C 自动继续
```

也不能简单做：

```text
UPDATE conversation SET objective = ...
```

因为旧 Agent 还在：

```text
goal v1 context
```

里面工作。

---

## 推荐行为

### Goal v1 → v2

例如：

```text
Goal v1:
分析基金 A 的风险

Tasks:
A 收集数据
B 风险分析
C 生成报告
```

用户修改：

```text
改成比较基金 A 和基金 B
```

产生：

```text
Goal v2
```

然后：

### pending / ready Task

直接标记：

```text
cancelled
```

原因：

```text
Superseded by Goal v2
```

不要删除。

### running Task

不要粗暴杀掉。

因为它可能已经：

```text
调用 Jira
写文件
调用外部 API
```

所以：

```text
running execution
    ↓
允许当前 execution 到安全边界结束
    ↓
task 不再向下游自动推进
```

如果当前 execution 最终返回，发现：

```text
task.goalRevision !== conversation.goalRevision
```

则：

```text
不允许它继续推进旧计划
```

而是交给 Lead。

# 8. Goal 修改实际上应该是一个 Replan Boundary

我建议把逻辑定义成：

```text
Goal v1
  ↓
Plan v1
  ↓
Tasks v1
  ↓
Executions v1
```

发生 Goal Change：

```text
Goal v2
  ↓
旧 Plan 失效
  ↓
Replan
  ↓
Tasks v2
  ↓
Executions v2
```

所以 Goal Revision 不只是 audit 字段。

它其实是：

> **Task Plan 的版本边界。**

这是整个设计最重要的语义。

# 9. 不要重新使用现在的 `plan_tasks`

当前代码里 `plan_tasks` 有非常明确的“一次性”语义，这是对的：

```ts
已有 Task → 拒绝重新 plan
```

不要把它改成：

```text
plan_tasks 可以无限重跑
```

否则原来的 Task history 会非常混乱。

我建议增加第二个 Core Tool：

```text
replan_tasks
```

语义：

```text
plan_tasks
    = 初次确定 Goal + 创建第一版任务计划

replan_tasks
    = Goal revision 后重新规划
```

这样非常清晰。

# 10. `replan_tasks` 怎么工作

例如：

```ts
replan_tasks({
  conversationId,
  memberId,
  objective,
  requirements,
  tasks
})
```

服务端一次事务完成：

```text
1. 创建 Goal v2
2. conversation.goal_revision = 2
3. 更新 conversation.objective
4. 更新 conversation.requirements
5. 旧 pending/ready tasks → cancelled
6. 旧 running tasks → 停止继续扩散
7. 创建新的 Tasks，goalRevision=2
8. COMMIT
9. Scheduler 启动 Goal v2 的 ready tasks
```

这样不会出现：

```text
Goal 已经 v2
但是新 Task 还没创建
Scheduler 又把旧 Task v1 启起来
```

# 18. 最终的状态关系应该变成这样

这是我建议你最终固定下来的模型：

```text
Conversation
│
├── Goal v1
│     ├── objective
│     ├── requirements
│     │
│     ├── Task A v1
│     │     └── Execution E1 v1
│     │
│     └── Task B v1
│           └── Execution E2 v1
│
├── Goal v2
│     ├── objective
│     ├── requirements
│     │
│     ├── Task C v2
│     │     └── Execution E3 v2
│     │
│     └── Task D v2
│           └── Execution E4 v2
│
└── Goal history
      v1
      v2
```

核心规则只有四条：

```text
1. Goal 可以变
2. Goal 历史不能改
3. Task / Execution 永远绑定创建时的 Goal Revision
4. Goal 变化 = 旧计划失效 + 新计划边界
```

## 是否“有必要做版本管理”

对于普通 Chat Agent：

```text
没有必要。
```

对于你现在这个：

```text
Conversation
+ Lead
+ 多 Member
+ 并行 Tasks
+ Scheduler
+ Persistent Execution
+ Human clarification
+ Jira / MCP / 外部写操作
+ Audit
```

则非常有必要。

因为你已经不是在做：

```text
Chat history
```

而是在做：

```text
long-running collaborative work
```

这时候 **Goal、Task、Execution 三者必须有明确的时间边界**。

我不会建议你再引入完整的 workflow engine、event sourcing、DAG version system。**一个 `conversation_goal_revision` + `goalRevision` 绑定到 Task/Execution，再加 `replan_tasks`，已经足够解决 90% 的问题，而且和你现在的架构非常自然地衔接。**
