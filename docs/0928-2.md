对于你这个 `team-member-copilot-agent`，我建议把“对话历史压缩”和“业务状态记忆”彻底分开。**不要自己再造一套完整的 conversation summarization 去替代 Copilot SDK 的 compaction。**

现在业界基本已经形成了比较明确的分层：

> **SDK/模型 Runtime 负责 Context Compaction；应用负责 Business State / Memory；原始对话永远保留。**

GitHub Copilot SDK 本身已经支持 Infinite Sessions，并且会在上下文接近阈值时后台自动 compact；当前 SDK 文档给出的典型配置就是 80% 开始后台压缩、95% 到临界点时阻塞并完成压缩。([GitHub Docs][1])

Anthropic、OpenAI、LangChain 这类方案也基本采用类似思路：**不要把“历史消息”“长期记忆”“当前工作状态”混成一个东西。** Anthropic 明确把 compaction、tool-result clearing、memory 分成三个不同层次；OpenAI 也提供 server-side compaction；LangChain 则把消息历史和长期 memory 分开。([Claude Platform][2])

# 1. 先明确你系统里有 4 种东西

你现在最容易混淆的是：

```text
Conversation History
        ↓
Agent Context
        ↓
Business State
        ↓
Long-term Memory
```

它们不是一回事。

### A. Conversation History

用户实际说过什么：

```text
User:
帮我分析这个投资方案

Lead:
好的，我先拆成三个任务...

User:
风险部分重点看监管风险

Lead:
明白...

Member:
我查到...

User:
另外加入流动性风险
```

这个东西：

**永远保留，不压缩，不覆盖。**

你的数据库应该是 source of truth。

---

### B. Agent Context

这是某一个 Agent 当前送给 LLM 的上下文。

例如：

```text
System Prompt
+
Agent Profile
+
Skills
+
Current Goal
+
Current Task
+
Recent Conversation
+
Selected Tool Results
+
Compaction Summary
```

这个东西可以压缩。

这正是 **Copilot SDK Infinite Session / Compaction** 应该负责的东西。

---

### C. Business State

例如：

```json
{
  "goal": "完成XX投资方案评估",
  "tasks": [
    {
      "id": "risk",
      "status": "running"
    },
    {
      "id": "compliance",
      "status": "completed"
    }
  ],
  "decisions": [
    "采用方案B",
    "监管风险需要进一步确认"
  ],
  "openIssues": [
    "流动性风险数据不足"
  ]
}
```

这个东西**不能依赖 LLM summary**。

应该由你的：

```text
Goal
Task
Execution
Decision
Approval
Artifact
Command
```

这些结构化数据负责。

这也是你现在架构里已经存在的 Task / Goal / Execution 模型真正应该承担的作用。

---

### D. Long-term Memory

例如某个 Member 长期知道：

```text
公司投资审核通常需要先看监管约束
这个团队习惯使用 XX 格式
这个成员偏好先做风险分析
```

这是：

```text
Member Memory
Team Memory
Project Memory
```

而不是某次 Conversation 的摘要。

Copilot SDK 现在也提供 session memory，但它属于另外一层，不应该拿它替代你的 Team/Member/Project knowledge model。([GitHub][3])

# 2. 所以：到底谁来 compress？

我的建议非常明确：

## 第一层：Copilot SDK 自动 compress

**负责 Agent 自己的上下文。**

例如：

```text
Conversation:
  500 messages
       ↓
Copilot Session
       ↓
Infinite Session
       ↓
80% → background compaction
       ↓
Compact context
       ↓
继续工作
```

Copilot SDK 当前已经支持：

```ts
infiniteSessions: {
  enabled: true,
  backgroundCompactionThreshold: 0.80,
  bufferExhaustionThreshold: 0.95,
}
```

并且会产生：

```text
session.compaction_start
session.compaction_complete
```

事件。([GitHub Docs][1])

**所以你没有必要自己写：**

```text
messages.slice(...)
↓
LLM summarize
↓
delete old messages
```

这种东西。

# 3. 但是你不能完全依赖 Copilot SDK

这里是关键。

Copilot SDK 解决的是：

> “LLM context 太长了怎么办？”

它没有解决：

> “这个业务做到哪里了？”

例如：

```text
第 1～80 轮
用户要求做投资分析

第 81～130 轮
Lead 与 Risk Member 讨论

第 131～200 轮
Developer 修改报告

第 201 轮
用户问：
“我们最终决定采用哪个方案？”
```

这时候单纯依赖 conversation compaction 是危险的。

所以你的系统还需要：

```text
Conversation
      ↓
Business State
      ↓
Goal / Task / Decision / Artifact / OpenIssue
```

这些东西要独立存在。

# 5. 对你的 Team/Member 模型，Session 应该怎么划分？

这是我认为你现在架构里非常重要的一点：

## 不要：

```text
Member Alice
   ↓
一个永远不断增长的 Copilot Session
```

否则：

```text
Team A conversation
Team B conversation
Task 1
Task 2
Direct Chat
```

最终会混在一起。

---

## 应该：

```text
Member
  +
Conversation
  ↓
Copilot Session
```

例如：

```text
sessionId =
  conversation:{conversationId}:member:{memberId}
```

所以：

```text
Conversation 123
 ├─ Lead
 │   └─ Copilot Session A
 │
 ├─ Risk Member
 │   └─ Copilot Session B
 │
 └─ Developer
     └─ Copilot Session C
```

而：

```text
Conversation 124
 ├─ Lead
 │   └─ Copilot Session D
 │
 └─ Developer
     └─ Copilot Session E
```

这样每个 Agent 都拥有自己独立的上下文。

Copilot SDK 本身也明确支持多个独立 sessions，而且 session ID 可以持久化和 resume。([GitHub][4])

# 6. 你的 Lead / Member 场景尤其不能把所有消息都塞进去

假设：

```text
User
Lead
Risk
Developer
Compliance
```

发生了 300 轮对话。

不能让 Developer 每次执行都看到：

```text
User 300轮
Lead 300轮
Risk 300轮
Compliance 300轮
...
```

正确方式应该是：

```text
Developer Context
    │
    ├─ Developer 自己的 Copilot Session
    │
    ├─ Current Task
    │
    ├─ Relevant Goal
    │
    ├─ Relevant Decisions
    │
    ├─ Relevant Artifacts
    │
    └─ Other Member Summary
```

也就是说：

**Agent-to-agent communication 应该传“工作结果”，不是传整个聊天记录。**

例如 Risk Member 给 Lead：

```json
{
  "task": "regulatory-risk",
  "status": "completed",
  "findings": [
    "Rule A applies",
    "Rule B does not apply"
  ],
  "openQuestions": [
    "Need confirm jurisdiction"
  ],
  "artifacts": [
    "risk-analysis.md"
  ]
}
```

Lead 再决定什么需要进入自己的 context。

这比：

```text
把 Risk Member 的 20000 tokens transcript
复制到 Lead context
```

可靠得多。

Anthropic 对 long-running agents 的实践也越来越强调这种“structured notes / external state + selective retrieval”，而不是单纯不断扩大 context。([Anthropic][5])

# 7. Tool Result 是另一个必须处理的问题

实际 Agent context 爆炸，很多时候不是聊天，而是：

```text
read_file
↓
10000 tokens

search
↓
15000 tokens

jira
↓
8000 tokens

snowflake
↓
20000 tokens

another tool
↓
12000 tokens
```

结果：

```text
Conversation       10K
Tool Results       65K
System/Skills      20K
```

这时候你单纯做 conversation summary 其实已经晚了。

Anthropic 现在就是把：

```text
Compaction
+
Tool-result clearing
+
Memory
```

分开处理。旧的、可以重新获取的 tool result 可以清掉，但记住“这个工具做过什么”以及最终结论。([Claude Platform][2])

所以你的架构应该：

```text
Tool Result
   │
   ├── 小结果 → 保留
   │
   ├── 大结果 → Artifact / DB / File
   │
   └── Agent context → pointer + summary
```

例如不要一直保留：

```text
Snowflake 返回 18,000 行
```

而是：

```text
Snowflake query executed
rows = 18,234
result = artifact://...
key finding = ...
```

需要的时候再检索。

# 8. 我甚至不建议你自己实现“Conversation Summary”

至少第一版不要。

很多系统容易设计成：

```text
Conversation
  ↓
每 20 轮
  ↓
LLM summarize
  ↓
conversation_summary
  ↓
继续
```

看起来简单，但会有一个严重问题：

```text
Summary 1
   ↓
Summary 2
   ↓
Summary 3
   ↓
Summary 4
```

错误会不断累积。

而且一旦用户 200 轮以后问：

> “第 17 轮我们为什么否定方案 A？”

summary 很可能已经把这个细节压掉了。

Anthropic 也明确指出 compaction 最大的问题就是**过度压缩可能丢失未来才会重新变得重要的信息**。因此他们同时强调 structured memory 和保留原始 context。([Anthropic][5])

所以你的数据库应该：

```text
conversation_message
    ↓
永远保留
```

而：

```text
Copilot context
    ↓
允许被 compact
```

这两个必须解耦。

对于这个项目，我会设计成：

```text
Layer 0 — System
────────────────────────

Personality
Policies
Capabilities
Skills

Layer 1 — Business State
────────────────────────
Goal

Current assignment
Decisions

────────────────────────

────────────────────────

────────────────────────

```

这比：

```text

```

要稳定得多。

# 10. Copilot SDK 在你项目里具体应该怎么配置

我建议直接：

```ts
const session = await client.createSession({
  sessionId: buildSessionId(conversationId, memberId),

  infiniteSessions: {
    enabled: true,

    // 80% 开始后台压缩
    backgroundCompactionThreshold: 0.80,

    // 95% 是最后保险
    bufferExhaustionThreshold: 0.95,
  },
});
```

Copilot SDK 当前就是按这个模型设计的。([GitHub Docs][1])

同时监听：

```ts
session.compaction_start
session.compaction_complete
session.usage_info
```

把这些作为 runtime telemetry：

```text
conversation_id
member_id
session_id

context_before
context_after
tokens_removed
messages_removed
timestamp
```

Copilot SDK 当前提供 `session.usage_info`，里面包含：

```text
currentTokens
tokenLimit
messagesLength
```

可以用来做 UI/监控。([GitHub][6])

Teams / ChatGPT 类产品未来可以显示：

```text

```

但不要显示：

因为没有删除。

可以显示：

```

甚至：

  12 tasks

```

这样用户不会误解“聊天记录被压缩以后就没了”。

# 12. 还有一个很重要的 Copilot SDK 问题

你现在已经在做多成员 / 多任务 / 多 replica，这一点必须注意：

**Copilot SDK session 本身不要被并发访问。**

GitHub SDK 文档明确写了，同一个 session 的 concurrent access 没有内置 locking，需要应用层自己做 lock/queue。([GitHub][7])

所以你当前的：

```text
MemberRuntime lock
```

方向是对的，但应该最终保证：

```text
conversation + member
        ↓
exactly one active SDK turn
        ↓
Copilot Session
```

尤其不能出现：

```text
User message
      ↓
Replica A

Member wake
      ↓
Replica B

同一个 Copilot Session
      ↓
两个 turn 同时进去
```

否则 compaction 本身也可能和另一个 turn 冲突。

这与你之前正在解决的 worker lease 问题其实是同一个问题的另一面。

## 对你当前项目，优先级我会这样定

**第一优先：直接启用 Copilot SDK Infinite Sessions。**

不用自己写 conversation summarizer。

**第二优先：把 Business State 做扎实。**

也就是：

```text
Goal
Task
Decision
OpenIssue
Artifact
Approval
```

这些成为 Agent 跨 compaction 的“事实来源”。

**第三优先：大型 Tool Result 外置。**

不要让：

```text
文件全文
Jira 全量结果
Snowflake 大查询
搜索结果
```

无限堆进 Copilot context。

**第四优先：Member × Conversation 独立 SDK Session。**

不要 Member 全局共享一个无限长 session。

**第五优先：把 compaction 事件纳入 telemetry/audit，但不要把 SDK compacted context 当成 Regulatory Audit Evidence。**

原始：

```text
ConversationMessage
ToolExecution
Command
Approval
Task
Execution
Artifact
```

仍然保留。

### 一个可以直接落到你项目里的规则

可以简单定成：

```text
Conversation Message
    = 永久事实

Task / Goal / Decision
    = 业务事实

Artifact / Tool Result
    = 可重新获取的外部事实

Copilot Session
    = 临时工作上下文

Copilot Compaction
    = runtime 优化机制

Member/Team Memory
    = 跨对话长期记忆
```

**这套边界我认为最适合你现在的 `team-member-copilot-agent`，而且不需要再引入一个很重的 Memory/Context Framework。**

还有一个值得注意的地方：Copilot SDK 的 Infinite Session 会自动 compaction，但 SDK 官方也明确说明 session 本身没有并发锁，而且 session persistence 需要持久化 workspace；这两个点对于你现在准备做的 K8s / 多 replica 架构比“怎么写 summary prompt”重要得多。([GitHub][7])
