## 架构重构：把 Copilot Session 降级为 Runtime 内部实现细节

**背景**：原骨架只有 React/Vite + Express + `copilot.ts` + `sessions.ts`，无持久化，
且 `Session` 被当作业务对象，会持续误导后续设计。

**结果**：按 `Member / Conversation / MemberRuntime / CopilotSession / Execution`
五层模型重写。文件结构与既定目标完全一致（server 15 个文件 + src 6 个文件），
删除 `server/routes/sessions.ts` 与 `src/components/Chat.tsx`。

### 新增/重写
- `server/domain.ts` — 五个业务对象的类型定义与边界注释
- `server/db.ts` — `node:sqlite`（`DatabaseSync`）+ 6 张表 + WAL + `foreign_keys=ON`
- `server/member-service.ts` — 长期 Member 身份，member home 落 `SOUL.md` / `memory/MEMORY.md` / `skills/`
- `server/copilot.ts` — 只负责 `MemberRuntime → CopilotSession`，含 `ask_member` / `remember_member`
- `server/team-service.ts` — 核心编排 + SSE 订阅 + delegation 守卫
- `server/app.ts` — 依赖装配（延迟箭头函数打破 CopilotService ↔ TeamService 循环）
- `server/routes/{members,conversations}.ts`
- `src/components/TeamChat.tsx`、重写 `src/lib/api.ts`、`src/index.css`、`README.md`

### 相对原始设计的 8 处修正（都是确定性 bug，不是风格偏好）
1. `streaming: true` — SDK 默认 false，不开 `assistant.message_delta` 根本不发，前端增量永远为空
2. `listMessages` 改为取**最近** N 条（原设计 `ORDER BY created_at ASC LIMIT n` 取的是最旧 N 条）
3. fire-and-forget 的 `executeMemberTurn` 补 `.catch()`，否则失败的 turn 变成 unhandled rejection
4. 新增 `config.executionTimeoutMs`（默认 10min）传给 `sendAndWait`，SDK 默认 60s 会把真实长任务判 failed
5. `ensureRuntime` 改 `INSERT OR IGNORE` + 回读，避免并发撞 `UNIQUE(conversation_id, member_id)`
6. SPA fallback 跳过 `/api/*`，未知 API 返回 JSON 404 而不是一份 HTML
7. 业务校验错误统一带 `status: 400`（原设计用裸 `new Error` → 500）
8. `errorHandler.ts` 抽出 `sendError/errorStatus/errorMessage`，消除 route 里 ~150 行重复 try/catch

## Runtime reliability（Commit 1 + Commit 2）

**背景**：`894e4f9` 的 Member / Conversation / Runtime / Execution / Delegation / SSE
已经成型，但只是「能跑的 Demo」。用户明确只做 Commit 1 + Commit 2（durable runtime
state + durable SSE），**不做** K8s sandbox / LLM router / policy service / MCP registry / scheduler。

解决的 5 个问题：① 无持久队列与恢复 ② SSE 易失 ③ runtime 锁只在进程内
④ 会话上下文与 Copilot session history 重复 ⑤ 并发 delegation 死锁。

### 新增文件
- `server/db-migrations.ts` — `PRAGMA user_version` 迁移（v1 → v2），无 migration framework
- `server/context-assembler.ts` — 增量上下文：只注入 `message_sequence > last_context_message_sequence`
- `server/recovery-service.ts` — 启动恢复（保守策略）
- `server/test/runtime-reliability.test.ts` — 19 个用例

### schema v2 变化
`conversation.event_sequence` / `message_sequence`、`conversation_message.message_sequence`
（+ UNIQUE 索引）、`member_runtime.active_execution_id` / `last_context_message_sequence`、
`execution.waiting_for_runtime_id` / `retry_of_execution_id`、`execution.status` 增加
`waiting_for_member` / `interrupted`、新表 `conversation_event`。

### 关键设计决策
- **不自动重跑 `running`**。Copilot session 可能已执行完工具但没落库，自动重跑会重复执行。
  要重做必须显式 `retryExecution()`，生成**新** execution 并用 `retry_of_execution_id` 指回。
- **`message.delta` 不落库**。token 级高频会写爆 DB；它不带 `id:` 帧，浏览器不推进
  Last-Event-ID，丢了由 durable 的 `message.created`（含完整内容）收敛。
- **`replayAndSubscribe` 用「先挂监听并缓冲 → 回放 → 补发缓冲」**，回放与实时之间不留缝。
- **回放必须翻页**（`REPLAY_BATCH=500`，上限 `REPLAY_MAX_EVENTS=5000`）。单次 `LIMIT` 截断
  会在「回放末尾」和「实时流开头」之间留静默空洞，比不回放更糟。
- **wait-for 环检测**（`detectDelegationWaitCycle`）：从 target 沿 `waiting_for_runtime_id`
  往前走，绕回 parent 就拒绝。检测 + 建 child + 标记父为 waiting 之间**不能有 await**
  （node:sqlite 同步 API 天然原子）。
- 父 execution 在委派期间进入 `waiting_for_member`，`finally` 里还原成**本来的**状态
  （不是硬编码 `running`）。
- `updateExecution` / `updateRuntime` 用 `!== undefined` 而不是 `??` —— 这两个字段需要能被
  显式清空为 null。
- `active_execution_id` / `waiting_for_runtime_id` 是**软引用**（不建 FK），避免与
  `execution.runtime_id` 形成循环外键。

### 迁移注意
- `user_version = 0` + 已存在 `member` 表 → 当作 v1（旧代码用 `CREATE TABLE IF NOT EXISTS`
  建的，从没写过版本号），**不能**当成全新库重建。
- `execution` 改 status 的 CHECK 要按官方 12 步重建表；`PRAGMA foreign_keys = OFF` 必须放在
  `BEGIN` **之前**（该 PRAGMA 在事务内无效），提交前跑 `PRAGMA foreign_key_check`。
- 升级时同步计数器：`conversation.message_sequence` 追历史最大值（否则下一条撞 UNIQUE）；
  `member_runtime.last_context_message_sequence` 推到当前最大序号（否则升级后立刻重复注入全量）。

## Runtime correctness + Execution API（Phase 3 的 Commit 1 + Commit 2）

**背景**：Phase 2 把可靠性打通了，但 Runtime 还不可操作 —— 没有 execution 查询面、
没有真 cancel。用户给的三条优先：① Copilot timeout → abort ② resumeSession 精确恢复
③ Execution API + cancel/retry。明确**不升级** `@github/copilot-sdk@1.0.14`（1.0.15-preview.3 先不碰）。

### 修的 5 个实现问题
1. **`resumeSession` 降级必须窄**（`isSessionNotFound`）。原来 catch 一切然后新建 session，
   等于把认证失败/网络故障静默变成「这是一轮全新对话」，丢掉该 Member 全部历史。
   匹配不上时问权威来源 `getSessionMetadata()`（缺失返回 `undefined`）；
   连查询都失败 → 原样抛出，不猜。
2. **`sendAndWait(timeout)` 不是取消**。SDK 文档明写 *does not abort in-flight agent work*。
   超时后必须 `session.abort()`，否则 DB 判 failed 而 Agent 还在跑。
3. **Conversation kind 形状约束进 Service 层**：`direct`=1、`group`≥2、`work`=1；
   只有 `group` 允许 `addMember` / `removeMember`。API 是公开的，不能靠 React 约束。
4. **SSE 与 `GET /messages` 竞态**：`TeamChat.tsx` 改成 `mergeMessages()` 按 id 去重 +
   按 `messageSequence` 排序，不再 `setMessages(result.messages)` 直接覆盖。
5. **归档 Member 的 roster 语义**：`hydrateConversation()` 不再过滤 `m.status='active'`。
   `requireConversationMember()`（宽松，认 roster）与 `requireActiveMember()`（严格，拒归档）
   拆成两个函数 —— 归档的人留在历史里，但不接新活。

### 新增 / 改动
- `server/copilot.ts` — `isSessionNotFound` / `isTurnTimeout` / `activeSessions: Map<executionId, CopilotSession>` /
  `cancelTurn()` / `acquireSession()` / `abortAndWaitIdle()` / `watchIdle()`；
  `createClient` 是测试用的 seam
- `server/routes/executions.ts`（新）— `GET /:id`、`POST /:id/retry`、`POST /:id/cancel`
- `server/routes/conversations.ts` — 新增 `GET /:id/executions?limit=`（默认 200，夹 1..1000）
- `server/team-service.ts` — `ExecutionCancelledError`、`cancelRequests: Set<string>`、
  `waitForRuntimeIdle()`、`cancelExecution()`、`listExecutions()`、cancel-aware `runTurn`
- `server/test/runtime-correctness.test.ts`（新，fake session/client seam）

### 关键设计决策
- **cancel 先停引擎，再决定终态**。反着写（先 `UPDATE status='cancelled'` 再 abort）造出
  「DB 说已取消、Agent 还在跑」的假取消，比不取消更危险 —— 它让操作者以为副作用已经停了。
  引擎收尾后状态若还是活的，直接 409，绝不硬写 cancelled。
- **`waiting_for_member` 的 cancel 返回 409**，第一版不做子树取消传播。
- **不做 `/executions/:id/tree`**。客户端按 `parentExecutionId` 自己组树，服务端算树只是缓存一个随时会变的视图。
- **abort 后必须先订阅 `session.idle` 再 abort**。ack 与 idle 之间有缝隙，事后订阅会漏事件、
  白等满 grace，把「已经停稳」误报成没停。（这一条是跑测试时发现的：两个用例各卡了 10s。）
- **abort 会让 `sendAndWait` 正常返回半截结果**（不是抛错），所以取消检查不能只放在 catch 里，
  否则被取消的 execution 会被记成 `completed`。`runTurn` 在 resolve 之后还要再查一次 `cancelRequests`。
- 被取消时把半截内容留在 `execution.response`：优先用引擎返回的 `partial`，退回流式累积的 `streamed`。
