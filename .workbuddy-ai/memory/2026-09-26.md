# 2026-09-26

## External Work System Adapter（Pivot B 落地）

把「外部工作系统」从「裸 jira_issue_key + JiraClient 直调」升级成薄适配层。
核心决策：**本地没有 JiraIssue 这个业务对象**，只有 `ExternalWorkRef`（引用）
和 `ExternalWorkSnapshot`（execution 开始时向 Jira 取证的最小字段）。

### 新增

- `server/work-management/types.ts` — `ExternalWorkRef` / `ExternalWorkSnapshot`
  / `WorkManagementProvider`（search / get / addComment / transition / assign）
  / `WorkRefFactory`（命名，单独拆出来因为是身份问题不是操作问题）
  / `WorkManagementRegistry`（查不到就抛，不静默跳过校验+取证）+ 序列化/解析 helper。
  `normalizeExternalWorkRef` 只校验形状，**不查存在性** —— 建会话路径上不该有网络调用。
- `server/work-management/jira-provider.ts` — `JiraProvider` 包住既有 `JiraClient`。
  换 MCP 传输时新写一个实现、装配处换一行，业务契约不动。
- `server/routes/work-management.ts` — `GET /providers` + `POST /jira/webhook`。
  webhook 做**最小投影**：按 key 或不可变 id 找房间 → 发 `external_work.changed`
  （payload 只有 `{ref, changedFields, receivedAt}`）。zod schema 刻意不声明
  `issue.fields`，未知键被剥掉 —— 「不复制工单」由解析器强制，不靠人记得。
  共享密钥用 `timingSafeEqual`；空 = 无门禁（与 internal/admin token 同一约定）。
- `server/test/work-management.test.ts`（22 例）
- `scripts/smoke-work-management.mjs` — 拉起真实 `dist-server` 的 smoke test
  （单测自建 express，验不到 app.ts 的装配）。

### 改动

- schema v12 → **v13**：`conversation.external_work_ref` 取代 `jira_issue_key`；
  `execution` 加 `external_work_ref` + `external_work_snapshot`，去掉 `jira_issue_key`。
  表达式索引 `json_extract(external_work_ref,'$.key')` 供 webhook 反查
  （SQLite 3.51，planner 确实走索引）。
- `TeamService`：`captureWorkSnapshot()` 在 runTurn 里**尽力而为**地取证 ——
  失败只 warn、不废掉这一轮（外部系统可用性不该变成平台的可用性）。
  `updateExecution` 里快照写一次就不再被覆盖。
- `JiraToolProvider` 改成吃 `WorkManagementProvider`（版本 1 → 2）；
  控制面与 Agent **共用同一个 Provider 实例**。`assign` 在 Provider 上有、
  但**刻意不暴露成工具**（改负责人是责任转移，要人指定 accountId）。
- 清掉 `projectId` / `workItemId` 残留：`src/lib/api.ts`、ConversationList /
  TeamSidebar / ConversationHeader / TeamSections、若干注释。

### 顺手修掉的两个真问题

1. `scripts/mutation-check.py` 有 **6 条变异打不上**（引用的 `claim` / `work_item_id`
   代码已被删）+ 3 条「断言抓不住」。前者删掉、后者补回断言。现在 **28/28 全绿**
   （改之前是 9 条不成立）。
2. `manifestHashOf` 的 tools 段**没记 Provider version**，而 `domain.ts` 明写
   `capabilityManifestHash` 覆盖「skill / knowledge / tool 三层的组成与版本」。
   补上 —— 否则「换了 tool provider 实现、声明没变」在审计链上完全看不出来。

### 踩到的坑（重复踩过，务必记住）

- **BSD grep 的 `\|` 交替会静默返回空**，又一次误判成「这个 API 不存在」。
  一律用 Grep 工具或 `grep -E`。
- 测试里 `process.env.DATA_DIR` 必须在 `import('../config.js')` **之前**设好，
  所以 config 也得走 `await import()` —— 静态 import 会被提升到模块体之前。
