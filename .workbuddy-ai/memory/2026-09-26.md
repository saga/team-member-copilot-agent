## 修 group 房间「用户提问、房间无人回答」（责任扩散）

用户截图：`arch review` 房间发「大家好」+「我希望做架构设计review，应该做什么」，
三个 Member **一条都没回**。查 `.data/team-member.db` 得到事实：6 条 execution
（3 人 × 2 条消息）全部 `status=completed`、`decision=skip`、`error=null`，
每条跑 10–14s。**机制完全正常，产品行为完全错误。**

根因是**责任扩散（bystander effect）**，不是模型偷懒：
`GroupDispatcher` 把用户消息以 `open_discussion` 广播给全体，而 prompt 告诉
**每个人**「没被点名 + 没东西可补 → 回 `<NO_REPLY>`」。三个人各自看都做了
合理判断，合起来是全体沉默。

### 修法：用户对着房间说话时，指定**唯一一名**应答者

- `GroupDispatcher.plan()`：`candidates` 算一次；`senderType === 'user'` 时
  `pickPrimaryResponder()` 选一人，其 `reason` 改成 `direct`，其余保持
  `open_discussion`。member 消息（follow_up）不指定 —— 顺带被唤醒的人才可以沉默。
- `pickPrimaryResponder()`：按 `last_replied_message_sequence` **升序**取第一
  （最久没发言的先答），平手按 `id` 定序。三条理由：判据是已有房间状态、重启后
  依然正确、天然轮流（不会永远同一个人回答）。**刻意不按 role 关键词猜**「谁最懂」
  —— 那是概率性路由，猜错了没法解释；要精确点名就用 `@handle`。
  `markReplied` 只在 `decision=reply` 分支调用（skip 分支提前 return），
  所以「最久没发言」是关于**发言**的事实，不是「被唤醒过」。
- `ContextAssembler.discussionInstruction()`：原来 `mustReply = direct || mention`
  共用一段文案。现在拆成三档 —— `mention`（用户点名）、`direct`（平台指定的
  应答者）、其余可沉默。**说辞必须分开**：告诉一个没被点名的人「用户点名了你」，
  模型可能先去纠正这个不存在的前提。`direct` 档显式写 "staying silent is not
  an option"，且**不出现** `<NO_REPLY>`。
- 关键：断言必须落在**渲染给模型的指令**上，不只是 `wakes` 里的 reason。
  reason 只是路由，真正改变行为的是模型读到的那段话。

## 负责人兜底 + 哨兵不再泄漏（用户提的两件事）

用户原话：「1）是否可以指定 leader / key contact 这类比较资深的角色，如果大家都不
发言，这个人应该负责回答。符合职场文化。 2）no reply 不要显示了，然后再消失，
显得很诡异。」

### (1) 负责人（RoomLead）与兜底 escalation

- schema v13 → v14：`conversation_member_state.is_lead` + **偏索引**
  `idx_conversation_member_state_lead ON (conversation_id) WHERE is_lead = 1`。
  「一个房间至多一个负责人」做成**数据库不变量**而不是代码约定 —— 违反时是静默的、
  极难排查。跨行约束不能写成列 CHECK，偏索引才对。
- `ConversationMemberService.setLead()`：一条
  `is_lead = CASE WHEN member_id = ? THEN ? ELSE 0 END` 同时表达「指定这个」和
  「其余让位」，**没有零负责人/两个负责人的中间态**，所以不需要事务。
  通知要发**两行**（新上任 + 被顶掉的），只发前者会让旧负责人在 UI 上一直挂 Lead 徽章。
- `WakeReason` 加 `'escalation'`；`GroupDispatcher.planEscalation()` 只做花名册判断
  （kind=group / 有负责人 / 负责人在册且 active / 未被静音），返回 null 而不是抛错。
- `TeamService.maybeEscalateSilentRoom()`：在**每条** skip 收口**之后**检查这一批
  是否全体沉默。必须在收口之后（之前它自己算 active，「跑完没有」永远是否），
  也必须在每条之后（只有最后收口的那条能通过「全部收口」这一关）。
- 指令单独一档，且必须写出「房间里没人说话」—— 那是这一档独有的信息。
- **设计反转（重要）**：一开始加了个「负责人已经被明确问过就不再兜底」的守卫，
  理由是「同一件事不做两遍」。它让兜底在**最常见**的场景里失效（负责人恰好就是
  被指定的应答者、拿着「你必须回答」也选择了沉默）→ 房间继续沉默。删掉守卫，
  改成断言「这种情况**仍然**兜底」。房间保持沉默的代价没有上界，多跑一轮有。

### (2) `<NO_REPLY>` 不再流到客户端

- `member-decision.ts`：`couldStillBeNoReply()`（容忍 `normalize()` 的外壳：代码围栏、
  引号、结尾句号）+ `NoReplyStreamGate`（`push` 扣住仍可能是哨兵的前缀，一旦分叉
  立即放行、零额外延迟；`flush(decision)` **必须**带判定 —— skip 时那条尾巴就是哨兵本身）。
- 接线在 `runWake` 的 `onDelta`，`flush` 放在 `message.created` **之前**
  （那条事件会清掉流式占位，之后再补 delta 会留下没人收的占位）。

### 这轮真正抓到的 bug

- **`asWakeReason()` 没跟上新枚举值**。原来是
  `v === 'direct' || v === 'mention' || v === 'follow_up' ? v : 'open_discussion'`，
  加 `'escalation'` 时漏改了 → **最强**的唤醒原因读回来被降级成**最弱**的。
  影响面：`RecoveryService`（`findLostWakes`）重放一条 durable 的兜底唤醒时，负责人
  拿到「你可以沉默」，兜底在重启后静默失效 —— 而那正是它最该起作用的时候。
  修法：改成 `Record<Exclude<WakeReason,'schedule'>, true>` 白名单 + hasOwnProperty，
  漏写新值变成**编译错误**。字符串比较不会报错，Record 会。
  （`'toString' in obj` 会穿原型链，所以用 `Object.prototype.hasOwnProperty.call`。）
- **`createConversationSchema` 里还留着 Pivot B 之前的 `jiraIssueKey`**：前端发
  `externalWorkRef` 被 zod 静默剥掉，每个挂 Jira 的会话都返回 `externalWorkRef: null`，
  HTTP 201、任何地方都不报错。已补 `externalWorkRef` 声明 + 8 条真实 HTTP 回归测试
  （含 `provider` 用 `z.literal('jira')`，坏值走 400 而不是 500）。

### 测试/工具链上的教训

- **`message.delta` 刻意不落库**（token 级事件写库会爆），所以「哨兵有没有漏出去」
  **不能查库断言** —— 那是空绿。必须从活的 `team.subscribe()` 抓。
  同理 stub 必须**逐字符**喂 `onDelta`，整段一次性到达时过滤路径根本没被走到。
- **变异脚本必须给测试加超时**。拿掉「已经有人回答过就不再兜底」这一关会让兜底
  自我循环 → 测试不红而是永远跑下去 → 脚本挂死；而脚本是用 `finally` 还原文件的，
  被 kill 就会在磁盘上留下一个**改过的源文件**（本轮真的留下了一次，
  `group-dispatcher.ts` 的 `reason: 'escalation'` 变成 `'open_discussion'`，已修回）。
  现在 `TEST_TIMEOUT_SECONDS = 60`，超时即判定变异被捕获。
- **`setLead` 不需要事务**：单条 CASE UPDATE + 偏索引已经保证原子性，且 node:sqlite
  是同步 API、语句之间没有 await，不可能交错。注释里已写明「一次 UPDATE 比一次事务
  便宜」，别再把它「修」成多语句 + 事务。

### 变异验证抓到的覆盖漏洞（不是坏变异，是缺测试）

第一次跑 45 条变异，44 条变红，**第 36 条「不等这一批跑完就兜底」仍然全绿**。
原因不是断言写错，而是**没有能区分它的场景**：光看「一次沉默只兜一次」的计数，
拿掉 `active` 守卫后计数**仍然是对的** —— `escalations > 0` 那道守卫把后续重复派发
都拦掉了。计数对，**时机错**（兜底在第一个 skip 收口时就派出去了，那时还有人在想）。

修法：真的造出守卫所保护的中间态 ——「两条 skip 已收口、bob 还挂在 running 上」。
这需要 **按成员** 挂住 turn：全局 `hold` 会把所有人都按住，于是谁都不收口，
被考的那条分支根本走不到。给 stub 加了 `holdMemberIds: Set<string> | null`
（null = 按住全部，保持原行为）。补测后该变异变红。

教训：**变异仍然全绿时，先问「有没有能观察这条分支的形状」，再问「断言是不是写错了」。**

### 第二条空绿：SSE 上不能对原始字节做字符串匹配

补了一条「客户端真正看到的东西」的断言（真实 express + 真实 SSE）。第一版
`body.includes('NO_REPLY')` —— **永远为 false，包括哨兵真的漏出去的时候**。

原因：`message.delta` 是**逐字符**的，每个字符各自包在一帧 `data: {...}` 里，
所以 `<NO_REPLY>` 这十个字符在原始 SSE 字节流里**从来不会连续出现**。
（另外第一版还拿 `event: execution.updated` 当「流是活的」证据 —— 但 execution
建出来时也发这条事件，它在 delta **之前**，于是断言在 delta 到达前就通过了。）

修法：解析 SSE 帧 → 把 `message.delta` 的 `delta` 拼起来 → 断言拼出来的文字。
并且等**终态**事件到达客户端（它排在那一轮所有 delta 之后），用它区分
「没看到哨兵」和「还没读到」。改完两条变异都能抓到，报错信息就是用户看到的东西：
`哨兵漏到客户端了： "<NO_REPLY>"`。

顺带：`scripts/smoke-work-management.mjs` 里写死了 `schema v13` 和
`user_version === 13`，schema 升到 14 之后它会静默失效。已改成从
`dist-server/db-migrations.js` 读 `SCHEMA_VERSION` —— 版本号写死在这个脚本里
是必然过期的，而且没有任何东西会提醒你。

### 全量套件里两个**既有**的 flake（不是本轮改动引入的）

收尾跑全量时偶发 1 条红。先做了归因再动手：`git worktree add /tmp/tmca-head HEAD`
拉一份**干净的 HEAD** 跑 15 轮全量 → **6/15 失败**。所以是既有的，与本轮无关。

**1. `team-v1.test.ts` → Scheduler → "Missing expected exception"（HEAD 4/15）**

根因：测试里两处**独立读时钟**，而断言要求它们**精确相等**。

```ts
const past = new Date(Date.now() - 1000).toISOString();
const once = createScheduleDue({ ... });   // 它的默认参数又读了一次 Date.now()
...
assert.throws(() => structure.insertScheduleRun(once.id, past));  // 靠 UNIQUE 撞上
```

`toISOString()` 带毫秒，两次读只要跨一个毫秒边界就不相等 → `scheduled_for` 差 1ms
→ 没有 UNIQUE 冲突 → insert 成功 → 报 "Missing expected exception"。
`createScheduleDue` 本来就有 `dueAt` 参数，测试没传而已。修法是把 `past` 传进去。

单跑几乎不复现（无负载，两次调用贴在一起）；全量跑时中间夹着有负载的调度才容易跨边界。
修完：**60 轮全量 0 失败**（含精确归因）。

**2. `governance-p0.test.ts` → "配置 ADMIN_API_TOKEN 后…"（HEAD 2/15）**

同一份干净 HEAD 上还会红这一条（`config.adminApiToken` 是模块级单例，与并行度/负载相关）。
**本轮没有动它** —— 记录在此，留给后续排查。修完之后 20 轮全量 + 25 轮单跑都没再复现。

**教训（测量方法本身出错过一次）**：第一版用
`grep -q "once 只 fire 一次"` 判断失败属于哪条用例 —— 但**通过**的用例名字也会出现在
输出里，于是任何失败都被误判成 Scheduler 那条。改成抓 `^not ok`（顶层套件名）
或一个只有真失败才会打印的精确标记（`DBG past=`），归因才可信。
**归因统计必须只匹配失败输出，不能匹配整个输出。**
